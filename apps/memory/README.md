# Memory

Workspace visual knowledge map for durable agent and user memory.

See the [retrieval and navigation architecture](../../docs/architecture/memory_navigation_architecture.md)
for shared services, detail levels, cursor semantics, queue hooks and local context views.

Memory keeps the human product surface graph-first. Under the hood it compiles workspace sources into an agent-optimized internal LLM Wiki made of compiled pages, atomic claims, citations, source links, compile runs, and lint findings. The compiled wiki is not a separate user-facing app or route; it is evidence visible from node inspection and from agent-facing context surfaces.

## Contract Notes

- Frontend, backend, CLI, and MCP entrypoints are declared in `app_contract.json`.
- Memory ships app-owned CLI and MCP descriptor sidecars at `cli/command_schemas.json` and `mcp/tool_schemas.json`. These populate `maverick app memory cli inspect memory --json` and `maverick app memory mcp inspect <tool> --json` with operation-specific descriptions and JSON schemas for current agent-facing operations.
- The frontend is a React/Vite graph workspace with a dark token-aligned canvas, live refresh, canvas graph navigation, readable node inspection, compiled wiki evidence, references, relationship browsing, and a create-node modal.
- The base-shell sidebar widgets provide Memory search, node navigation, a footer context-preview action that opens the app modal, and an icon-only create action that opens the app create modal.
- The contract declares the bundled `memory-ops` skill, persisted view-state actions, `memory_compile`, `memory_lint`, `memory_wiki_query`, `memory_ingest_source`, `memory_source_query`, `memory_fetch_chunks`, `memory_inspect_source`, `memory_jobs`, `memory_ingest_storage_source`, `memory_apply_storage_staleness`, and the `node` reference entity.
- The contract declares required Storage interfaces for local file identity and bounded file content reads, plus an optional Google Drive provider dependency for Drive indexing workflows. Memory calls Storage through official platform-hosted surfaces; direct local Storage entrypoint fallback is limited to explicit test/development mode with `MAVERICK_MEMORY_ALLOW_LOCAL_STORAGE_FALLBACK=1`.
- App-owned storage lives under `data/memory/` for the SQLite graph, internal wiki tables, attached artifacts, and the verified source/chunk content store.
- Memory storage schema v8 retains v4's explicit current source-version pointer, supporting/conflicting evidence relations, active-node content identities, revision snapshots, and compiled claim FTS. Upgrading from v4, v5, v6 or v7 revokes supporting verification and invalidates existing active compiled pages until the candidate propositions have been checked with the numeric-format/sign/operator/question-aware criterion. Recompilation prevents citing a numeric prefix when an operator continues the expression after a paragraph break. Deduplicated recompilation also reconsiders previously unverified evidence beside UUIDs and locators. Existing node text, original evidence and confidence are preserved.
- Memory is one of the repository reference apps for complete stateful contract coverage.

## Runtime Behavior

- Frontend backend calls derive the mounted app id from `/apps/<mount_app_id>/...`, so workspace-local forks use their local backend mount instead of a hardcoded `memory` route.
- Frontend backend calls normalize HTTP and app-level errors and support abort/timeout handling for stale requests.
- The graph canvas uses pointer gestures across desktop and mobile: drag empty space to pan, drag a node to move/select it, pinch to zoom, and wheel to zoom on pointer devices.
- The graph action returns a lightweight node/edge summary for canvas and sidebar rendering. Full external references and edge details are loaded through `inspect`.
- `compile` deterministically builds the internal wiki page for a node from the current node text, external references, app-owned source links, and relationships. It records source/version/chunk provenance in the compile run, emits a redaction-safe `memory_compile_completed` event, creates claims, and refreshes lint findings without calling an LLM yet. Supporting citations require equivalent ordered assertions, with compatible negation, numbers, dates, units and participants. Lexical overlap discovers candidates but never establishes support. Recognized opposing assertions are stored separately as contradictions; unknown paraphrases remain unverified, with relevant passages available separately for review. Original passages and SHA-verified chunks are preserved; remote Storage citations include the Storage source version used for ingestion. Quote ranges are stored only when they can be mapped back to the stored source chunk body.
- The source foundation separates logical source identity from deduplicated immutable versions and chunks. `sources.current_version_id` records the current observation, including A → B → A. `source_documents` are stable source identities, `source_versions` capture observed hash and extraction state, and `source_chunks` carry verified content-store paths, hashes, ranges, and locators when bounded extracted text is available.
- The content store writes canonical UTF-8 Markdown under `data/memory/content/sources/` and `data/memory/content/chunks/` using SHA-derived relative paths. Reads verify the stored body hash, absolute paths and traversal are rejected, and front matter remains non-authoritative metadata outside the body hash.
- Storage file references are split into `local_storage_file` and `remote_storage_file`. Local files may use `workspace_relative_path` under `storage/uploaded/` or `storage/generated/`. Remote files, including Google Drive files, must reference `owning_app_id=storage`, `entity_type=file`, a stable `file_...` Storage entity id, and remote metadata such as `provider`, `connection_id`, `drive_file_id`, `source_version`, and `display_path`.
- Memory never treats Google Drive as a workspace path and never receives Google tokens. Remote source ingestion asks Storage for bounded preview text using the stable Storage file reference; Storage remains responsible for Drive OAuth, export/download policy, provider capabilities, and remote bytes.
- `memory_attach_file` remains a link-oriented compatibility surface. Citation-ready local or remote source content should be ingested through `memory_ingest_source`; legacy attached workspace paths are revalidated before any filesystem hash read and degrade to `reference_snapshot` when the stored path is invalid or unavailable.
- `memory_ingest_source` provides generic app-owned source ingestion for `inline_markdown`, local `storage_file` sources, remote `remote_storage_file` payloads produced by Storage `drive_index`, and `app_entity` reference snapshots from another app's official reference summarize/resolve surfaces. Local Storage file ingestion accepts a stable Storage file id or a workspace-relative Storage path, verifies that both identify the same Storage file when both are supplied, and resolves metadata and content through official Storage `reference_resolve`, `file_info`, `preview_text`, and bounded text `read_file` surfaces before Memory writes its own verified source/chunk content store; previewable PDFs and Office files use Storage preview text, and non-extractable files become `reference_snapshot` versions without chunks. When Storage exposes a file SHA-256, Memory records the source version as `file_bytes` while keeping the canonical body hash on the stored content. Remote Storage file ingestion reuses the same validation and materialization path as the transitional `memory_ingest_storage_source` action and rejects mismatched `entity_id`/`file_id`. App-entity ingestion never reads the owner app's private database; it stores a redaction-safe reference snapshot with the owning app id, entity type, entity id, and deep link as source locator. When compiled, linked app-owned sources can produce chunk-level citations just like Storage-backed sources when they include credible extracted-reference text.
- Source-version `hash_kind` values are limited to `canonical_body`, `file_bytes`, `remote_storage_preview`, and `reference_snapshot`. Remote Storage versions use `remote_storage_preview` only when Storage returns bounded preview text; otherwise Memory records a `reference_snapshot` instead of implying a content hash.
- `inspect` defaults to a compact card. Explicit `detail` selects `content`, `evidence`, `sources`, `history` or an unbudgeted `full` audit read. Content and revision bodies page by characters under a byte budget; history returns headers without snapshots. Evidence pages claims with at most three citations of each relation and supports citation paging via `claim_id`; pending compilation still exposes current source-chunk references. Batch `get_nodes` retrieves up to twenty cards. Full audit reads retain removed references and recent snapshots.
- `explore` is the agent/UI graph navigation service: one to five seeds, incoming/outgoing/both, kind filters, one hop by default or explicit depth two, scope, edge limit, cursor and byte budget. Recursive traversal is depth-bounded, tracks shortest visited distances and deduplicates edges by id; parallel edges and cycles survive. Responses include compact endpoint cards, hop, edge direction through source/target identity, reasons, confidence basis, revision/state, snapshot id and explicit continuation. Unavailable/excluded/out-of-scope seeds are reported separately.
- `context` preserves the 9,500-byte default, compact provenance and evidence, and reserves up to two critical neighbors for contradictions/supersessions even at a full textual limit. `retrieval_has_more`/`search_next_cursor` describe further search; `omitted_for_budget`/`budget_omitted_node_ids` describe byte omissions; per-card `details_available` describes further detail. Totals are exact only when the first page is exhausted; otherwise `total_candidate_count` is null. Retrieval reasons, user confirmation, verification, compilation and validity stay separate.
- `search` defaults to cards, or adds compact source matches/proof with `detail=evidence`. Node/wiki/claim/current-source candidates are ranked together in SQL before pagination, using weighted FTS, term coverage and importance. Stable node/person/project ids, alias arrays and app reference ids match directly. `wiki_query` shares FTS ranking and scope; `source_query` shares tokenization, scope and progressive continuation and verifies returned original excerpts. Original `fetch_chunks` reads retain SHA verification. `inspect_source` keeps its explicit version/chunk pagination and retained audit controls.
- Paged responses use request-bound cursors and a read revision. Changing retrieval parameters or data rejects a stale cursor explicitly; page size and byte budgets may change while continuing. `has_more`, `next_cursor`, `omitted_for_budget` and `stop_reason` distinguish result limits, byte stops and exhaustion. Reads do not write shared view state or access telemetry unless explicitly requested.
- Memory declares platform `background_tick` and `backend_recovery` hooks. They run at most three compile/lint jobs per tick, stopping between jobs after two seconds (one job can take longer), with one OS-held maintenance lock per workspace, lease recovery, retry backoff and deduplication. Same-node compile/lint leases serialize across explicit runners too. Ticks request 15-second backlog or 60-second idle scheduling. The frontend has no maintenance interval. Source ingest/reindex requiring fresh Storage or app authority remains explicit; the worker never scans Drive or restores a removed source.
- `lint` refreshes app-owned findings such as missing citations, contradictions, orphan nodes, empty content, and stale compiled pages, and emits a redaction-safe `memory_lint_refreshed` event with counts instead of source text. When Storage metadata reports remote source staleness or a non-healthy sync state, Memory marks the compiled wiki stale so the source can be re-indexed through Storage.
- SQLite connections enable foreign keys, WAL, `busy_timeout`, and explicit write transactions. Read-time schema checks inspect version and table shape only. Writes maintain FTS incrementally. Full file/hash integrity checks and index repair require explicit `maintenance` with `verify_index=true`; returned chunks still receive SHA verification.
- Numeric request fields reject non-finite values, and SQLite constraint failures are returned as validation errors instead of crashing entrypoints.
- Context retrieval does not write audit telemetry by default; `record_access_event` is opt-in. Inspect, context and wiki query compute freshness without persisting writes. Explicit lint, ingestion and maintenance persist derived state. Opt-in access telemetry commits its transaction.
- Context and evidence search discard unsupported source match channels after passage integrity/query checks. Verification pages candidates per node, so a long source cannot hide another node, and continues beyond damaged prefixes until a verified sample or exhaustion, retaining at most three valid passages per node. Source-only failures are omitted without losing indexed continuation or byte-budget bounds. Critical continuation detects additional contradictions or supersessions even when only one relation kind exists.
- Compact cards expose a `state_revision` for changes to compilation, evidence, queued work, active sources and attached references without rewriting the fact revision. References invalidate sections and cursors even before compilation or while the wiki is already stale. The selective inspector refreshes its sections/previews on that state change and preserves live verification when subsequent sections return indexed indicators.
- Sidebar search text is widget-local. Persisted view-state changes are reserved for explicit view actions such as `set_custom_view`, `set_view_filter`, and `clear_custom_view`.

## Facts, Retrieval and Management

`ingest_source` accepts explicit `operation` values: `attach_evidence` retains curated text, `update_fact` changes the current fact, and `replace_fact` records the replaced revision. Use `fact_body`, `fact_summary` and `fact_metadata` when approved knowledge differs from the evidence passage; `expected_updated_at` rejects changes to a reviewed node revision. Generated document nodes track their current source text; curated notes retain their text and expose conflicts for reconciliation. Identical inline and remote Storage ingestion preserves the reference revision, keeps an already current page fresh and adds no ready work. Remote observations use the source version's `observed_at`; unchanged observations do not advance the reference's content revision. Compilation hashes include the persisted metadata after synchronization.

Repeated `remember` calls deduplicate identical active content within type/person/project/knowledge/validity scope. New unspecified confidence defaults to 0.5; zero is always preserved. `confidence_basis` distinguishes unspecified input, agent inference, user confirmation and documentary evidence. Existing confidence values are not retroactively changed.

Search gathers node, compiled page, claim and current-source candidates before applying the final limit. Weighted FTS5, term coverage and current evidence produce a ranking score, not a probability. Complete term matches precede partial matches; source evidence can outrank partially matching notes. Optional `project_id`/`person_id` scope is applied before paging across search, context, graph, exploration, wiki and source queries. `as_of` filters `valid_from`/`valid_until` at a date (today by default); `include_expired` and `include_unscoped` are explicit. This filters validity metadata; it does not reconstruct overwritten facts from revision history. Ordinary related expansion requires relation weight and confidence of at least 0.5. Critical contradictions/supersessions are included separately even below that threshold, with uncertainty explicit. Sidebar and graph use these backend results without a second title-only filter.

Compact context projects bounded text directly in SQL, batches selected-node evidence and refs, preserves knowledge type, confirmation, scope, validity and conversation provenance, and omits stale compiled facts. Card state is an indexed observation; selective evidence/full inspection observes live source currency, and original passage reads verify integrity. Its context `body_text` is always a bounded excerpt of the current node fact. Source excerpts stay in dedicated evidence fields, including passages contradicting a correction; they never replace that fact. Supporting verification preserves numeric signs and decimal separators, including `.5`, `+.5`, `-.5` and leading-comma decimals, and rejects interrogative passages. Shared proposition extraction preserves complete expressions, including malformed decimals and operators on either side of paragraph breaks (LF, CRLF and whitespace-only blank lines), while separating neighboring assertions and source headers. Compilation checks already loaded neighboring chunks to prevent expression fragments spanning chunk boundaries from supporting or contradicting a claim; complete neighboring assertions remain usable and original chunks retain their offsets. Numeric validation applies to each candidate proposition; UUIDs, file locators and URLs retain their literal spelling as opaque tokens. Unsupported arithmetic, exponents, grouping, fraction glyphs, superscripts and malformed numbers stay unverified without blocking unrelated propositions. Numeric values are compared without rounding for conflict detection; supporting verification retains literal numeric spelling. Unrecognized meanings remain unverified. Compilation reads each candidate chunk once and reuses completed runs when the input hash is unchanged.

`merge_nodes` transfers evidence and relationships into an explicitly chosen target while preserving its fact text. `exclude_node` reversibly removes knowledge from normal retrieval. An excluded node can be restored or deleted with revision guards; correction, verification and merging require restoration first, and their controls are disabled while excluded. Node deletion and `remove_source` retain audit content while suppressing ordinary source retrieval; they do not delete the original Storage or other app record. A shared active-source filter excludes removed references from full search, direct and related-node context, wiki results and Storage reference projections, including preview/export requests and cached preview metadata. Inspection retains removed external references and source versions for audit. Ordinary compilation and maintenance respect removal. Explicit remote reimport restores a removed source and queues reconciliation; maintenance alone never restores it. Inspection and management use revision guards where supplied. See [audit validation](../../docs/development/memory_audit_validation_2026-10-11.md) for regression coverage and measured limits.

## Agent-First Drive To Memory Contract

Memory is the knowledge and retrieval layer for Storage-hosted Drive content. It consumes stable Storage references; it does not become a Drive client and does not receive Google secrets.

The operating contract is:

- Storage discovers Drive files, reads/export/previews their content, owns Drive sync, and produces `memory_source` payloads from `drive_index`.
- Memory accepts `local_storage_file` for workspace Storage paths and `remote_storage_file` for Drive files. Remote references must use `owning_app_id=storage`, `entity_type=file`, stable `entity_id=file_...`, and metadata containing `provider=google_drive`, `connection_id`, `drive_file_id`, and `source_version` when available.
- Memory rejects `workspace_relative_path` for remote Drive providers and must never persist Google tokens, refresh tokens, OAuth codes, or Drive filesystem paths.
- During compile, Memory may request bounded preview text from Storage through official Storage surfaces using the stable Storage file reference. Storage remains responsible for Drive permissions, export limits, temporary cache policy, and bytes.
- Memory citations and source links must keep enough Storage metadata for an agent to return to Storage for preview, export, reference resolution, or deep-link display. Citation payloads expose `source_version` and, when backed by Storage, a nested `storage_reference` usable with `storage_drive_preview`, `storage_drive_export`, or `storage_reference_resolve`.
- Storage-originated staleness is applied through `apply_storage_staleness` / `memory_apply_storage_staleness`, which consumes `drive_sync.memory_staleness`, marks every linked Storage ref with stale metadata and sync state, marks impacted compiled wiki pages and claims stale, and returns impacted nodes plus a bounded `storage_drive_index` re-index suggestion. Memory does not scan Drive. Rich Storage payloads may include `connection_id`, `drive_file_id`, current `source_version`, and `indexed_source_version`; Memory preserves those fields in the ref staleness metadata and re-index suggestion.

The target autonomous workflow is:

1. The agent asks Memory first through `memory_context`, `memory_search`, or `memory_wiki_query`.
2. If the answer needs fresh Drive evidence, the agent searches or navigates Drive through Storage.
3. The agent calls `storage_drive_index` for selected files.
4. The Memory `memory_ingest_source` action with `adapter_id=remote_storage_file` consumes the returned `memory_source`, optional `node_id`, optional `title`, optional bounded `preview_text`, required `source_version`, and `compile_after_ingest`. If `node_id` is omitted, Memory creates or reuses a file-backed node for the stable Storage `file_...` identity. If `node_id` is present, Memory attaches or updates that Storage source on the target node without moving the same Drive file away from other nodes that already cite it.
5. After Memory ingest succeeds, the agent acknowledges the Storage side with `storage_drive_mark_indexed`, passing the same `stable_storage_file_id`, `source_version`, and when available `memory_node_id`, `memory_external_ref_id`, and `memory_source_version_id`. This prevents Storage from advertising files as indexed before they are actually in Memory and gives later sync diagnostics a trace back to the Memory ingest.
6. Retrieval returns compact compiled summaries, claims, citations, source versions, verified source chunk identifiers when available, and Storage reference metadata; expansion surfaces return full node or chunk bodies when needed.
7. When the document itself needs to be shown, the agent goes back to Storage with the citation/reference and calls the appropriate preview, export, or reference surface.

Operationally, agents should keep the loop selective:

- Stop at Memory when `memory_context`, `memory_search`, or `memory_wiki_query` returns fresh enough evidence.
- Search or navigate Drive only when Memory is missing, stale, or the user explicitly needs fresh Drive material; select a bounded candidate set rather than indexing a folder or all Drive.
- Hand off `storage_drive_index.memory_source`, `preview_text`, `preview_truncated`, and `source_version` directly to `memory_ingest_source` with `adapter_id=remote_storage_file` and `compile_after_ingest=true` when immediate reasoning is needed, then call `storage_drive_mark_indexed` after Memory succeeds. `memory_ingest_storage_source` remains available as a transitional alias.
- Use `storage_references[].preview_request`, `storage_references[].export_request`, `citations[].storage_reference`, or `deep_link` from Memory retrieval to show the document through Storage. Memory never serves raw Drive bytes.

Remote Storage ingest is idempotent by stable Storage file id when no target node is provided, and idempotent by `(node_id, stable_storage_file_id)` when a target node is provided. This lets one Drive file support multiple Memory nodes while avoiding duplicate refs on the same node. It requires a Storage `source_version` so source versions and citations remain stable. A successful ingest clears prior Storage stale metadata for that file reference and materializes the matching source document, source version, content-store body, and source chunks before compile when preview text is available; an empty preview response records a `reference_snapshot` version without chunks. When `compile_after_ingest=true`, Memory also compiles immediately into claims, citations, and a compiled wiki page. If Storage preview/export cannot be called and no bounded `preview_text` was supplied, ingest fails without creating a fresh source version or fresh wiki page.

The first v3 implementation keeps existing Drive-to-Memory behavior intact while adding the migration, content-store foundation, deterministic multi-chunk source extraction, chunk-level citation support, app-owned source chunk FTS, read-only source/chunk retrieval primitives, source chunk matches in node retrieval, an app-owned job lifecycle with `run_next` plus bounded `run_until_idle`, and `memory_ingest_source` for `inline_markdown`, local workspace `storage_file` sources, remote Storage file payloads fetched through Storage-owned file surfaces, and app-entity reference snapshots. Memory currently reaches Storage and app reference surfaces through the platform-hosted `maverick app ... mcp` wrapper with bounded timeout and retry settings; a future direct app-to-app SDK can replace that transport without changing Memory's stored source model. Embeddings and model-assisted entailment remain optional future work; this implementation adds no inference dependency or cost.

`apply_storage_staleness` accepts the Storage sync payload shape, for example `owning_app_id=storage`, `entity_type=file`, `entity_id=file_...`, and `reason=google_drive_change`, plus optional Drive locator and version fields. It updates every matching `external_refs` row for that Storage file identity and leaves re-indexing explicit: the agent should call Storage `drive_index`, then Memory `memory_ingest_source` with `adapter_id=remote_storage_file` and `compile_after_ingest=true`. The queued `requires_storage_reindex` job is an inspectable action-required marker; `run_next` returns the re-index suggestion and completes that marker without attempting an impossible Memory-only ingest.

## SDK Flow

Validate the installation-level Memory source directly:

```bash
./scripts/maverick core cli run core.app-sdk.validate --app-id memory --app-root apps/memory --workspace default --json
```

Workspace-local registration and installation commands target a workspace-owned copy under `workspaces/default/apps/memory`:

```bash
./scripts/maverick core cli run core.app-sdk.register-local --app-id memory --workspace default --json
./scripts/maverick core cli run core.app-sdk.install-local --app-id memory --workspace default --json
./scripts/maverick core cli run core.app-sdk.status --app-id memory --workspace default --json
./scripts/maverick core cli run core.app-sdk.package --app-id memory --workspace default --json
```

## Context UI and renderer

The UI loads 30 cards initially and displays at most 40 at a time. Selecting a
node calls the same `explore` service as agents, inserts its neighborhood into
the graph (including Chat deep links), and supports more connections and back
navigation. Content, Connections, Sources and History load independently.
Correction requires the complete fact body, preventing a partial excerpt from
overwriting a longer fact. A keyboard-navigable list accompanies the canvas.

React Force Graph 2D is the single graph engine, loaded on demand. Its Canvas/D3
layout gives the map fluid movement, node dragging and animated pan/zoom; settled
nodes drift within small orbits. App-owned vector icons, subtle colored halos,
focus highlighting and directional particles make neighborhoods readable. Curved
parallel links retain their identities; arrows and selection expose direction,
type and reason. Incremental updates preserve simulation objects and positions
without mutating retrieval cards. Native fit/zoom/motion controls and the memory
list remain usable when layout is frozen. Animation stops when the document or
graph is hidden. Reduced-motion preferences disable movement and camera
transitions by default; explicitly resuming motion overrides that preference for
this view. The mobile inspector leaves the upper map visible. See
[navigation validation](../../docs/development/memory_navigation_validation_2026-10-11.md)
for measured query/byte costs, renderer build size and verification.

Context reads return identifiable reference sets (`view.node_ids`,
`view.snapshot_id`); opening them via `context_node_ids` (JSON string) and
`context_snapshot_id` is local to that frontend. It never changes the persisted
workspace filter. Reopening shows current cards; the original response's node
revisions are the historical reference, not a persisted UI snapshot.
