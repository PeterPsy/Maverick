# Settings

Admin-only platform settings app for provider/runtime settings, users, workspace roles, workspace assignments, app visibility, and core persistence adapter operations.

## Contract Notes

- The app currently declares frontend, CLI, MCP, and base-shell sidebar widget surfaces.
- `settings` intentionally does not declare an app-owned backend or lifecycle hooks yet; authoritative admin state remains core-owned.
- Persistence adapter status, platform settings, provider/model selection, runtime-session cleanup, and backend restarts are core-owned admin surfaces. Settings presents those surfaces in the UI.
- Platform settings includes **PC use decision model**, independent of the conversation model. Core persists the workspace's provider, model and reasoning effort through `/api/settings/computer-use`; the initial selection is Codex Luna `low`. Choices come from the installed image-capable Codex catalog. Changes apply to the next bounded UI task, and unavailable saved selections do not silently fall back. Other decision providers require an executable Core operator adapter before appearing in this selector.
- The platform settings panel reconciles Core's installed native model catalog using its bounded cache before grouping selectable agent models into `CLI models` and `API models`, then by provider (for example Codex, Antigravity, and OpenRouter). Provider subscription allowance is shown on the dedicated Usage page, separately from model configuration. Rows keep model and reasoning prominent, while binding, credential, default and policy controls remain available when a row is expanded. Settings never owns a static Codex model list. Plain hosted text has no Settings model family, while internal generation and historical sessions retain the lower-level compatibility path. Speech-to-text and synthesis remain separate: file/one-shot transcription uses Nova-3 over `/v1/listen`, realtime conversation uses Flux over WebSocket v2, and TTS keeps its own hosted choices.
- PC use choices require a successfully discovered Codex catalog with explicit image support. A discovery failure cannot admit a generic fallback model. Runtime inventory refreshes preserve unsaved decision-model edits. Workspace generations and request versions fence old saves, including leaving and returning to the same workspace while a save is pending.
- Settings loads only the resources required by the selected page. Users reads users and workspaces without requesting model catalogs, runtime sessions or persistence. Each resource has its own loading/error state, retry and in-flight deduplication; navigation aborts superseded reads and rejects their late responses. Existing data remains available after a failed refresh.
- The default page is Models & providers. AI includes Models, Voice, PC use, Usage and Conversation learning; Workspace includes Users & access, Workspace apps and App links; System includes Sessions, Cache and Persistence. Existing `pages/platform-settings` links resolve to Models. User profiles and workspace assignments share the same selected user, and Workspace apps provides the Core-authorized workspace creation form.
- Rendering reconciles app-owned DOM nodes instead of replacing the root. Inputs, disclosure state and chart islands survive unrelated updates. A bounded page cache retains unsaved form controls during navigation; workspace changes clear it. Voice/routing/operator drafts have separate saved baselines, scoped acknowledgements and explicit discard actions. Retained controls receive one current event handler.
- Sidebar search keeps the input mounted, searches setting keywords, and forwards bounded control targets for default models, voice, passwords, PC use and cache.
- Sessions defaults to the active workspace even in Default. An authorized admin can explicitly switch to the server view. Search/status filters and 20-row pagination bound the DOM. Every deletion confirms the concrete session count, scope and active-agent effects and submits explicit ids; the UI never interprets an empty selection as server-wide cleanup. User deletion and browser cache clearing also use focus-managed confirmation dialogs. Persistence reports observed phases without fabricated percentages.
- App links limits dependency inventory reads to four concurrent apps and fences outdated workspace responses. App identities come from the current registry, with a generic fallback instead of app-id icon maps.
- Main and sidebar frontends apply shell dark/light tokens before paint and validate live theme messages through the exact-parent protocol. The app uses an inner scroll area and the declared mobile shell offset.
- Core `GET /api/settings/platform?section=context|models|voice|computer-use` projects the requested resource and publishes redaction-safe `Server-Timing` phase durations. The unqualified read remains the complete platform projection for existing Core consumers. Models does not compose PC use or recovery; context does not probe provider catalogs and PC use reads only the operator catalog. Usage charts load their React module only on the Usage page.

- Text-to-speech controls live in Voice → Speech model settings → Text to speech. The optional `text-to-speech` app link resolves a `speech.synthesis` provider; its backend owns the workspace engine and BCP-47 language settings. The controls show available Gemini, Kokoro and local engines, use optional Core Secrets delivery, save only synthesis fields, and keep transcription settings independent. Stale responses are fenced when the workspace changes; loading and provider errors leave the other settings usable.
- Settings uses Core's effective-capability and data-policy projections to gate remote controls. The compact model rows show availability, reasoning and activation, with credential, cost and workspace policy controls in the expanded row. Contained remote controls remain blocked by the server-owned posture; the effective snapshot is never a client capability override. No fake-data consent, data-class checkbox or client credential authority exists. Quarantined runtime rows expose `recovery_required` with only an allowlisted public reason instead of arbitrary Core diagnostic detail.
- During a frontend/backend rollout, missing effective-capability or attestation projections render as unavailable instead of aborting the settings panel. Remote agentic enablement fails closed until the active backend publishes an active effective-capability snapshot.
- The runtime inventory shows one card per exact model inside each execution family and model provider, rather than repeating historical or alternative profile definitions. The enabled workspace default takes precedence, then another enabled, selectable, enable-eligible or Full Workspace-available profile, and finally the highest naturally ordered revision. `/api/settings/platform` returns this compact Settings projection while the dedicated agentic administration APIs retain complete revision history. Binding IDs/CAS and existing session pins remain unchanged.
- A disabled native connection with a healthy installed runtime and an authenticated catalog offers `Enable <provider>` in its Models heading. This explicit platform-admin action uses `POST /api/providers/native/activate`, then reloads Settings. It restores the connection without changing workspace model switches. Runtime tokens and non-admin users cannot activate connections through this endpoint.
- Agentic providers that declare `supports_subscription_usage` expose compact redaction-safe used/remaining percentages, quota-window durations, and renewal countdowns on the Usage page. Settings loads all workspace-visible supported providers independently through the admin-only `GET /api/providers/usage` surface and keeps the rest of the platform settings usable when an upstream usage service is unavailable. Codex credentials and Antigravity's operator-managed OAuth profile remain server-side; the browser receives only plan, model-group, percentage, reset-window, availability, and credit summary fields. Antigravity quota reads use the CLI's read-only `/usage` command inside a temporary confined runtime home.
- The Usage page loads core-metered workspace token history from the admin-only `GET /api/usage/timeseries` surface. A single chart defaults to non-cached tokens and retains explicit cached-input and processed-total details. Admins can select the metric, provider, and model above the chart, then choose a bounded time range from the button row below those filters; ranges through three days use hourly UTC buckets and longer ranges use daily UTC buckets. The chart describes locally observed runtime consumption across root and delegated sessions; cumulative lifetime counters observed when metering attaches to an existing provider thread establish a baseline instead of inflating the first bucket. It remains separate from provider subscription percentages and does not claim coverage before metering was enabled.
- Persistence migration UI must call the core dry-run endpoint before apply. The confirmation dialog exposes target JSON/Mongo connection fields, including Mongo username and password secret ref, and source cleanup is an explicit operator opt-in rather than the default migration behavior.
- The main app iframe owns the settings work surface and renders one page at a time: models, voice, PC use, usage, users/access, workspace apps, app links, learning, sessions, cache, or persistence.
- The app links page presents generic core app dependency selections for the active workspace, including intra-app provider catalogs such as `agent.catalog`. It calls `/api/apps/dependencies` and does not read another app's private storage.
- The `settings-sidebar` iframe declared for `shell.sidebar.primary` is a page navigator, matching the page-list pattern used by Docs Studio. Selected-user controls live inside the relevant Settings pages.
- The main page and sidebar validate shell messages against the exact parent window and the platform origin injected into the isolated iframe. Navigation, selection and visibility messages do not require the shell and Settings to share an origin; local relay duplicates are ignored.
- The platform settings panel is rendered inside the main app work surface rather than as a shell modal or app-local overlay. It calls generic core settings/provider/runtime APIs and keeps the shell boundary app-agnostic. Initial `/api/settings/platform` loading excludes runtime-session projection; the cleanup inventory is fetched independently through `/api/settings/runtime-sessions` only when Sessions is visited.
- Conversation learning at `pages/learning` manages Chat-owned analysis settings, serial queue, evidence review, Memory saving/guarded undo and improvement implementation tickets. Both result channels have Kanban/list views, search, categories, open/closed filters, source evidence and work-chat/project links. Accepted Memory runs one chat at a time; improvements have configurable parallel capacity (four by default). Runtime completion sends improvements to verification; Memory becomes saved only after the provider confirms the write. Status, exact review/queue counts and daily allowance precede compact output-channel controls and the results inbox. Timing/model, usage/retention and exclusions are collapsed by default. Captured chats have short evidence labels, and empty states explain prospective capture. Pause/resume sends a partial settings update; refresh preserves drafts, while explicit discard clears them. Live invalidations use the SDK shell stream, are workspace-scoped, suspend while hidden, and preserve drafts, selection and focus. Read epochs fence outdated responses after a mutation, and evidence/Memory links target the injected shell origin. It calls Chat's backend and generic dependency-selection APIs; Settings owns no copies of chat or Memory data.
- Learning copy distinguishes a quiet period from completed work. Cards explain general value, reassessment holds and evidence-backed dismissal reasons; development requirements are excluded from Memory.
- The app stores only admin UI preferences under `data/settings/preferences.json`.
- `reference_entities`, `data_events`, and persisted `view_surfaces` remain intentionally empty until the app grows app-owned administrative state instead of acting as a shell over core-managed records.

## Frontend Structure

The app remains a TypeScript/Vite work surface, with React mounted only for reusable UI components. Tailwind CSS 4 and the shadcn alias contract are configured in `components.json`; because Vite's source root is `frontend/src`, the canonical shadcn UI path for this app is `frontend/src/components/ui`.

## SDK Flow

```bash
./scripts/loopino core cli run core.app-sdk.validate --app-id settings --app-root apps/settings --workspace default --json
./scripts/loopino app settings frontend build --operator --json
python3 -m unittest discover -s apps/settings/tests -p 'test_*.py'
python3 scripts/test_suite.py --app settings --level integration --jobs 1
```

`settings` is an installation-level sealed app under `apps/settings`; it is not a workspace-local app project. Do not use `core.app-sdk.register-local` or `core.app-sdk.install-local` for this app unless it is intentionally copied into a workspace-local development project.
