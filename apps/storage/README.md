# Storage

Workspace file storage for uploaded files and generated artifacts.

## Contract Notes

- Frontend, backend, CLI, and MCP entrypoints are declared in `app_contract.json`.
- Storage ships app-owned CLI and MCP descriptor sidecars at `cli/command_schemas.json` and `mcp/tool_schemas.json`. These populate `maverick app storage cli inspect storage --json` and `maverick app storage mcp inspect <tool> --json` with operation-specific descriptions and JSON schemas instead of generic `{"type":"object"}` fallbacks.
- Calling the app-owned CLI command or the generic `maverick_storage` MCP tool without arguments returns the compact `operations.manifest` payload. Catalog reads are explicit through `action: "catalog"` or the dedicated `storage_list_files` MCP tool, and callers should pass `limit` for bounded pages.
- Storage exposes dedicated MCP read-path tools for common agent workflows: `storage_list_files`, `storage_file_info`, `storage_read_file`, `storage_read_text`, `storage_preview_text`, `storage_preview_table`, and `storage_file_localize`. Storage does not expose host filesystem paths or internal `file_response` payloads through CLI or MCP; callers use Storage references, stream URLs, or file content payloads. The generic `maverick_storage` tool remains available for less common actions.
- The contract now declares the bundled `storage-ops` skill, persisted storage view-state actions, the base-shell `storage-sidebar` and `storage-sidebar-footer` widgets, and the `file-preview` chat widget.
- `file` and `folder` are reference entities. App-owned state lives under `data/storage/state.json`; the derived file and folder inventory lives under `data/storage/files.json`.
- Storage is one of the repository reference apps for file- and folder-centric references and embedded widget surfaces.
- The Storage view surface currently declares only `file` for standard custom view composition; folder references are searchable, resolvable, summarizable, and deep-linkable, but custom views remain file-only.
- File records expose stable `file_<uuid>` ids that survive Storage-managed rename and move operations. `path_id` keeps the legacy `uploaded:<path>` or `generated:<path>` value as navigation metadata.
- Storage records are provider-aware. Local Uploaded and Generated files expose `provider: "local"`, keep `role`, `relative_path`, and `workspace_relative_path`, and include normalized `capabilities`, `sync_status`, `indexed`, and `stale` metadata. Remote providers such as future Google Drive entries must use `provider: "google_drive"`, `connection_id`, `drive_file_id`, and `remote_locator`; `workspace_relative_path` remains local-only and is rejected for remote provider requests.
- Storage keeps JSON byte payloads deliberately bounded. Inline local writes through `upload_file`, `write_file`, and `file.content.write` remain capped at 25 MiB, while inline reads and folder ZIP payloads remain capped at 100 MiB for CLI/MCP compatibility. The CLI-only `upload_local_file` action wraps Storage-owned `local_upload_session.start`, `local_upload_session.chunk`, `local_upload_session.status`, and `local_upload_session.cancel` with 8 MiB decoded chunks for trusted local source paths, so binary outputs can be saved without putting large base64 payloads on the shell command line. Sandbox invocations may upload only source files inside the workspace root; full-access operator invocations may upload other readable local paths. The lower-level session actions remain available for clients that need manual resume control, and clients never send a 500 MiB JSON body. Browser downloads for local files and folders use authenticated `/api/apps/<app_id>/media`; folder media downloads stream an app-approved temporary ZIP file and enforce the same 500 MiB transfer ceiling. Drive resumable upload and Drive media/cache limits remain provider-specific.
- Google Drive is declared as a remote Storage provider, not as a separate Drive app. Storage requests Google OAuth client secrets as workspace app secrets and stores `google-drive-refresh-token` only through Core Secrets/Vault as a resource-scoped app-managed secret with `resource_type=drive_connection` and `resource_id=<connection_id>`. Memory and agents must use Storage references, preview/export, search, and indexing surfaces rather than Google tokens or local filesystem paths for Drive content.
- Drive OAuth supports explicit `full_read`, `full_rw`, and `picker_limited` modes. The product default is `full_rw`; the start response includes the selected mode, and OAuth state, connection records, audit entries, frontend payloads, and agent-facing JSON do not persist or return Google access or refresh tokens. OAuth completion is a mounted-backend callback action because it returns `platform_secret_writes`; MCP and CLI expose start/list/disconnect plus file operations, not the callback completion surface.
- Drive OAuth completion matches an existing active connection for the same Google account first on Google subject id and then on normalized account email. When the same account is connected again, Storage treats it as a reconnect: it reuses the existing `drive_connection` id, rotates the connection-scoped refresh-token grant, removes the pending OAuth record, and avoids duplicate Drive account entries.
- `GoogleDriveProvider` is the Storage-owned remote provider adapter. It refreshes access tokens from Vault-delivered app secrets, keeps only a short-lived local access-token cache under Storage temporary app data, lists Drive roots (`My Drive`, `Shared with me`, and Shared drives when Drive exposes them), lists children by Drive parent id with Drive `pageToken` cursors, and runs bounded Drive search through `drive_list_roots`, `drive_list_children`, and `drive_search`. Provider responses are normalized as Storage file/folder records with `provider: "google_drive"`, `connection_id`, `drive_file_id`, deterministic `file_<hash>` Storage ids for files, derived `display_path`, Drive capability mapping, and an empty `workspace_relative_path`.
- Drive list calls use narrower Google corpora where possible: `My Drive` and `Shared with me` use `corpora=user`, Shared Drive folder navigation uses the parent `driveId`, and only unscoped Drive search falls back to `allDrives`.
- Drive content access stays behind Storage read, preview, and export surfaces. Binary Drive files are fetched with `files.get?alt=media` only after Storage has resolved metadata and Drive capabilities from the persisted Storage record when available, falling back to Google metadata otherwise; every read requires `max_bytes` within the existing Storage read limits. Google Docs, Sheets, and Slides are exported through the centralized Storage Drive exporter: readable text and preview requests choose text/plain for Docs/Slides and CSV for Sheets, while explicit PDF/DOCX/XLSX/PPTX requests choose the corresponding Google export MIME type.
- Browser-streamable Drive image, video, audio, and PDF files can be localized through `file.localize` / `storage_file_localize`. Storage downloads the Drive blob once with server-side Google credentials, stores it under the budgeted `data/storage/drive_local_cache`, records checksum, source version, progress metadata, ETag, and stream URLs, and serves those URLs through authenticated `/api/apps/<app_id>/media`. The internal `file.media_stream` action is accepted only from that mounted media route, not from CLI or MCP. The same media route can proxy authorized Drive byte ranges when the full local cache is missing, and no-range Drive downloads stream from Drive to the browser while Storage writes the durable cache. `HEAD` requests return metadata headers without downloading Drive bytes. Stream URLs must carry `source_version`; localized URLs also carry `localization_id`, while direct URLs without `localization_id` are current stable-file-id URLs bound to the supplied `source_version`. Storage validates the supplied version and any supplied localization id before serving. The core media route supports `HEAD`, `Accept-Ranges: bytes`, `206 Partial Content`, `Content-Range`, `ETag`, and forces attachment disposition for non-media or scriptable MIME types such as HTML and SVG. Drive tokens and local host paths are never exposed to the browser.
- `drive_index` prepares a bounded Memory ingestion payload from Storage-owned Drive preview/export and a stable Storage reference. It returns `status: "ready_for_memory"`, non-empty `source_version` from Drive revision metadata, `preview_text` capped at 20,000 characters, `preview_truncated`, and a `remote_storage_file` reference with `stable_storage_file_id`. When Drive preview downloads a supported binary Office file instead of returning text directly, Storage applies its bounded text extractor before deciding whether the file is indexable. It marks the Storage inventory record as `ready_for_memory`, not indexed. After Memory ingest succeeds, agents call `drive_mark_indexed` with the stable Storage file id, source version, and optional Memory ack ids; that acknowledgement marks the file indexed, records the Memory trace metadata, and clears prior stale state so later Drive sync can emit Memory staleness only for files that actually reached Memory.
- Google Drive `files.export` is capped at 10 MB. Storage rejects larger requested export budgets with an agent-facing validation error before fetching, and maps Google export failures into clear `drive_export` errors. Drive preview/export responses and short-lived access-token cache entries use bounded temporary cache files under Storage app data with TTL and total-size pruning. Durable workspace-governed Drive bytes are created only by explicit `file.localize`, currently limited to browser-streamable media/PDF and bounded by the Storage localization byte budget. The durable Drive media cache also enforces an app-level budget, TTL cleanup, LRU eviction, stale-source cleanup after Drive sync/version changes, and free-disk preflight checks before new cache writes.
- Drive write access is exposed only through dedicated Storage write/delete actions, separate from Drive list/search/read tools. `drive_write` uploads a new binary file into a Drive folder or updates binary file content where the Drive API allows media updates; `drive_rename`, `drive_move`, and `drive_trash` perform the corresponding remote mutations. Each mutation resolves the stable Storage file id or `connection_id + drive_file_id`, refreshes metadata through Storage-owned secrets, validates Drive capabilities before the API call, persists the updated remote file record, and appends a redaction-safe audit event under Storage Drive connection state.
- The Storage frontend can upload local files into the active Google Drive folder from app-level drag/drop and from the sidebar footer. Small uploads call `drive_write` through Storage with the connection-scoped Drive refresh-token selector and keep Google tokens server-side. Larger Drive uploads use Storage-owned Google resumable sessions with chunk progress, cancel, retry, and remote offset refresh after ambiguous chunk failures.
- `drive_trash` is fail-closed: callers must pass `confirm: true` or an explicit `delete_policy` value before Storage will call Drive. Missing Drive secret grants fail before any Google request and return only generic grant errors, not raw token, refresh token, client secret, or authorization material.
- `drive_sync` uses the Google Drive change feed. The first sync for a connection stores `changes.getStartPageToken` as both `start_page_token` and `last_processed_page_token`; later syncs call `changes.list` with the persisted cursor, process paginated changes, and persist the next page token or final new start token. The connection's `sync_state` records `start_page_token`, `last_processed_page_token`, `last_sync_at`, `status`, and a redacted `error`. Incremental changes update the Storage catalog, rename and move display paths, mark removed or inaccessible files as stale, and return `stale_storage_file_ids` plus `memory_staleness` payloads that Memory can consume through declared app surfaces. Those staleness payloads include the stable Storage file id, Drive locator, current source version, last indexed source version when known, and structured staleness/sync metadata. Storage does not perform a full Drive scan when the change feed cursor is available.
- Drive `display_path` and breadcrumb values are navigation metadata only. Identity remains the stable Storage file id plus `connection_id` and `drive_file_id`; removed or inaccessible Drive files are marked with remote status metadata rather than being resolved through the local filesystem.
- `file_info` accepts stable `file_id` values through the Storage resolver, so callers can resolve a file without depending on its current local path. Local path references remain supported for existing Uploaded and Generated workflows.
- Folder references use path-based percent-encoded ids such as `generated:Client%20Docs/`; they resolve only while that visible folder path exists.
- Catalog results default to newest workspace storage artifacts first, using filesystem modification time with path order as the stable tiebreaker.
- Catalog supports server-side `query`, `role`, `kind`, `folder_path`, `file_ids`, `workspace_relative_paths`, `offset`, and `limit` parameters. `folder_path: ""` means the selected storage root's direct files, while an omitted `folder_path` leaves folder scoping disabled. `references.search` and `references.resolve` use the inventory instead of recursively scanning storage on each call, and expose both workspace files and visible Storage folders to generic `@` reference pickers such as Chat.
- Catalog returns files and folders from one inventory refresh snapshot. Normal catalog calls reconcile known files plus changed directories so out-of-band workspace files appear without requiring frontend callers to pass `sync: true`.
- Storage-managed upload, write, Markdown update, folder create/delete, rename, move, batch move, and delete actions hold the workspace Storage write lock while they validate paths, touch bytes, enforce quota, and update `files.json`.
- Storage hides upload implementation folders such as UUID buckets and presents those uploaded files at the visible Uploaded root.
- The Uploaded and Generated storage roots render as top-level folder cards in the Storage browser.
- Folder cards expose details, ZIP download, drag-to-move, and delete actions; ZIP downloads in the browser stream through the authenticated media route instead of returning a base64 archive in JSON. Storage root folders can be downloaded and used as move targets but not moved or deleted.
- Destructive file and folder deletes use an app-rendered confirmation dialog instead of browser modal APIs so the mounted Storage iframe works under the shell sandbox policy.
- The Storage browser requests one bounded page of the current folder or search view at a time. When no search query is active, the backend filters direct child files by `folder_path`; a non-empty `Search in Storage` query searches folders and files across Uploaded and Generated storage at once while file-type filters still refine matching files.
- Direct navigation to a file resolves the target by stable id or workspace-relative path, exits custom/search scoping, reloads the file's containing folder, and then merges the resolved file into the visible page if it is outside the first page.
- The breadcrumb heading shows direct folder and file counts plus the current folder's recursive size in MB.
- After server-confirmed upload, rename, Markdown edit, move, create, or delete actions, the frontend patches the loaded catalog snapshot immediately and then revalidates the authoritative catalog in the background. The backend remains the source of truth; the fast visual update is not applied before the server accepts the mutation.
- Users can create folders inside `storage/uploaded/` and `storage/generated/` from the sidebar's selected folder, and drag Storage files or folders into visible folder cards or sidebar tree folders. Moves stay inside the item's current storage role; folder moves reject root folders, path escapes, name collisions, and attempts to move a folder into itself or a child folder.
- Storage drag payloads allow both move and copy operations: Storage folder targets use them for within-role moves, while Chat can read the same file, folder, or selection payloads as copy-style citations in the floating/full composer.
- Long-pressing a visible file or movable folder enters selection mode, showing selection toggles on the current screen. Dragging a selected item moves the selected files and folders together into a visible folder card or sidebar tree folder through one `move_items` backend action under one Storage write lock, or cites the selected files and folders when dropped into Chat, using the same item payload as single-item drags.
- Users can upload a local file from the sidebar into the selected Uploaded, Generated, or Google Drive folder. Local Storage validates the target folder and refuses silent overwrites; files above 25 MiB and up to 500 MiB use Storage-owned local upload sessions with chunk progress, retry, cancel, and resume from the last acknowledged offset. Small Google Drive uploads use Drive create semantics, while larger Drive uploads use Storage-owned resumable sessions. Both local and remote paths return the new Storage record.
- Users can also drag local files onto any part of the Storage app to upload them into the currently displayed folder, with animated feedback for ready, uploading, success, and blocked states.
- The frontend supports animated list and card layouts so users can switch between compact file rows and visual file cards. Google Drive cards render icon and metadata only; streamable Drive bytes are localized for preview/download only after the user opens or downloads the file, and the preview modal/widget point media elements at the authenticated stream URL instead of creating base64 Blob URLs. Non-Google-native Drive binaries download through the same authenticated media route instead of the bounded JSON/base64 preview path.
- Drive localization exposes `file.localize_status`, `file.localize_retry`, and `file.localize_cancel` for progress-aware callers. `file.local_path.resolve` is a governed backend-only operation for trusted internal consumers that need a local Storage file path or a Drive file already localized into Storage's controlled cache; it is reachable when a consumer app returns a core `dependency_backend_requests` item after selecting Storage for the `file.local.path` interface. The core verifies the selected provider declares the `backend` surface and asks Storage's `surface=secret_selector` preflight to derive Drive grants from either `connection_id + drive_file_id` or a stable Storage file id before delivering secrets. The resolved local path is delivered only to the consumer backend callback, while public dependency-backend result envelopes contain status metadata. `file.local_path.resolve` is not declared through MCP, CLI, ordinary mounted backend HTTP, or frontend helpers. Ordinary preview/localize responses do not expose local filesystem paths to the browser.
- `file.reconcile` refreshes Storage inventory from local workspace storage or refreshes one known Drive metadata record. It is intended for generated outputs, cache records, and external app writes that need Storage metadata realigned without changing folder download behavior.
- Storage contributes its file-type filter rail, navigation tree, and folder actions through base shell sidebar widget slots instead of rendering a separate in-app sidebar; the rail shows only file types currently present in workspace storage.
- The sidebar file-type rail forwards the saved `view_filter` through the shell event detail so the mounted Storage app can apply the filter immediately, then refresh the catalog page against that filter.
- The app-level `Search in Storage` control searches files and folders globally across workspace storage; the sidebar navigation tree mirrors that shared view-state query instead of exposing a separate folder search.
- CSV and XLSX previews expose structured rows to the frontend so the preview modal can render spreadsheet-like tables instead of plain delimited text.
- Text, Markdown, CSV, and XLSX previews are bounded by server-side byte, row, column, and archive budgets before extraction. Agents that need the document body should call `storage_read_text` / `file.text.read` instead of treating preview output as complete source text; that read path extracts supported text, Markdown, DOCX, PPTX, and XLSX files without the preview character cap and returns `text_char_count`, `offset`, `range_end`, `has_more`, and `next_offset` for deterministic windowed reads.
- Markdown previews render common Markdown structure, including headings, lists, code blocks, links, blockquotes, and pipe tables, in both the Storage app and the file-preview widget instead of showing raw Markdown text.
- The file-preview chat widget renders the file body as one neutral Chat-style document box with a compact clickable title row, keeps the skeleton visible until inline preview content is ready, posts bounded height updates, renders PDF page 1 through PDF.js canvas instead of a nested browser PDF iframe, provides explicit open/download fallback actions, and groups fullscreen/open/download actions beside the title.
- Markdown files can be edited from the Storage preview modal with a source editor and live rendered preview, copied in full to the clipboard, then saved back to the same validated workspace storage path.
- The Storage preview modal header exposes a fullscreen toggle; it uses the browser Fullscreen API when allowed and falls back to an in-app fullscreen layout when iframe policy blocks native fullscreen. On mobile, the preview modal fills the app viewport below the shell header with borderless chrome, truncates long titles on one row, hides the fullscreen action, fits image previews inside the available box without cropping, and renders content directly below that header.

## Agent-First Drive To Memory Contract

Storage is the file gateway for Google Drive and any future cloud storage provider. Memory is the durable knowledge and retrieval layer. Agents orchestrate the two apps through official Storage and Memory CLI/MCP surfaces; there is no user-facing or manual "index this Drive file" step in the intended workflow.

The operating contract is:

- Storage owns Drive discovery, navigation, metadata sync, bounded preview, bounded export, and stable file references.
- Storage is the only app that receives Google OAuth client secrets or Drive refresh-token grants from Core Secrets/Vault.
- Memory consumes only Storage references such as `owning_app_id=storage`, `entity_type=file`, `entity_id=file_...`, `provider=google_drive`, `connection_id`, `drive_file_id`, and `source_version`.
- Memory must not receive Google tokens, call Google APIs, treat Drive as a local filesystem, or persist Drive files under `workspace_relative_path`.
- `drive_index` is the Storage handoff operation for agents. It returns `status: "ready_for_memory"`, bounded `preview_text`, `preview_truncated`, non-empty `source_version`, normalized `file`, and `memory_source.source_kind=remote_storage_file`. It does not claim Memory ingest has succeeded. After `memory_ingest_storage_source` succeeds, the agent calls `drive_mark_indexed`; only then Storage marks the file indexed for future `drive_sync` staleness and clears stale inventory state after a successful re-index. `drive_index` fails clearly when Drive does not grant download/export access, when export limits are exceeded, when revision metadata cannot produce `source_version`, or when the selected file cannot produce text suitable for Memory ingestion.
- `drive_sync` reports remote changes as `memory_staleness` items with Storage file identity. Agents can pass each item to Memory's `memory_apply_storage_staleness`; Memory decides which memory nodes, claims, citations, and compiled wiki pages are impacted and returns the bounded re-index suggestion.

The expected agent workflow is:

1. Query Memory first with `memory_context`, `memory_search`, or `memory_wiki_query`.
2. If Memory lacks fresh evidence, discover Drive content through Storage using `storage_drive_connections_list`, `storage_drive_list_roots`, `storage_drive_list_children`, or `storage_drive_search`.
3. Select a bounded candidate file and call `storage_drive_index`.
4. Pass the returned `memory_source`, `preview_text`, and `source_version` to Memory's `memory_ingest_storage_source` action with `compile_after_ingest=true` when immediate retrieval is needed. Memory deduplicates by the stable Storage file id and stores only the Storage reference plus bounded extracted text needed for Memory retrieval.
5. After Memory ingest succeeds, call `storage_drive_mark_indexed` with `stable_storage_file_id`, `source_version`, and when available the Memory node/ref/source-version ids to acknowledge that this Drive file really reached Memory.
6. Use Memory retrieval for reasoning and citations.
7. When the source document must be shown, resolve the Storage citation/reference and call `storage_drive_preview`, `storage_drive_export`, `storage_file_localize` for stream URLs, or `storage_reference_resolve`; do not ask Memory for raw Drive bytes, local host paths, or ungoverned filesystem paths.

For agent orchestration, `storage_drive_index` is the indexing handoff and `storage_drive_mark_indexed` is the post-ingest acknowledgement. `storage_drive_index` is appropriate after a specific candidate file has been selected by search/list metadata, and inappropriate as a bulk crawler. Its output is already shaped for Memory: pass `memory_source`, `preview_text`, `preview_truncated`, and `source_version` through unchanged, then acknowledge only after Memory returns success. Later, Memory retrieval should lead the agent back to Storage by returning a `preview_request`, `export_request`, `reference_resolve_request`, or `/app/storage/files/<file_id>` deep link.

This deliberately avoids blind full-Drive indexing. Agents index only relevant files, make those facts reusable through Memory, and keep all remote file access behind Storage.

## SDK Flow

```bash
./scripts/maverick core cli run core.app-sdk.validate --app-root apps/storage --app-id storage --workspace default --json
./scripts/maverick core cli run core.app-sdk.status --app-id storage --workspace default --json
```

`validate --app-root apps/storage` is the authoritative source-tree check for this installation-level app. `status --app-id storage` is a partial SDK diagnostic aimed at workspace-local app projects; for Storage it may report `source_exists: false` or a failed binding when the install-level source is absent or unhealthy. Use `maverick apps list --json` to verify that Storage is actually mounted in the active workspace.

`register-local`, `install-local`, and `package` operate on workspace-local app projects under `workspaces/<workspace_id>/apps/<app_id>/`; they are not the correct flow for this installation-level Storage app source.
