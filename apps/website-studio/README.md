# Website Studio

Website Studio is a source-available Maverick app for importing, indexing, editing, previewing, diffing, approving, and maintaining company website projects inside a workspace.

This implementation covers Phases 1, 2, Website Studio's app-side Phase 3 publish orchestration, and the Website Studio-owned Phase 3A runtime/governance work described by this repository's app contract, tests, and README. Public custom-domain hosting, certificates, CDN/cache enforcement, and production binding remain post-1-2-3-3A platform work until core exposes generic hosting surfaces. This is a real working app, not only a scaffold.

## Source State

- App id: `website-studio`
- Publisher: `maverick`
- Distribution: `source_available`
- Source access: `forkable`
- Source root: `apps/website-studio`
- Workspace data root: `workspaces/<workspace_id>/data/website-studio`
- Primary data: `data/website-studio/app.sqlite` and `data/website-studio/sites`

Website Studio currently runs as a platform app source. `maverick apps list --json` is the right workspace binding check for that posture. `maverick core cli run core.app-sdk.status --app-id website-studio --json` reports workspace-local project registration state and may show `source_exists=false` for this app even when the platform source is installed and enabled.

The versioned Phase 1-3A acceptance boundary is documented in [`docs/phase-1-3a-acceptance.md`](docs/phase-1-3a-acceptance.md).

- Install, migrate, and health-check hooks

## Phase 1, 2, 3 App Orchestration, And 3A Behavior

Website Studio supports multiple site records. Each site owns a working source tree under `data/website-studio/sites/<site_id>/source`. Sites can be archived, restored, renamed, duplicated, and selected as the active workspace site without deleting their source or revision history. The active site is persisted in Website Studio view state so the sidebar, main app, and agent context surfaces agree on the selected site; archived sites cannot be selected as active. ZIP import validates archive members in a staging directory before replacing a source tree, rejects traversal, symlinks, OS executables, sensitive source files, excessive file counts, and ZIP upload size-limit violations, normalizes common single-folder export roots, classifies the source as `full_source`, `static_export`, or `partial_source`, records the Storage artifact reference when provided, then indexes static pages, sitemap XML routes, simple redirect routes, SEO metadata, and assets into the sitemap payload. Git import clones a public GitHub HTTPS repository or an app-local repository path into staging with prompt/credential helpers disabled, removes `.git` metadata for Phase 1, rejects symlinks, executable files, sensitive source files, excessive file counts, and bounded source-tree size-limit violations, classifies the imported source tree, then indexes the working source. ZIP and Git imports also return a deterministic `source_profile` with source shape, static preview support, framework hints such as Vite/Astro/Next/Gatsby, and package-manager hints from lockfiles; this detection never installs dependencies or runs imported code.

`website_git_connection_prepare` records a GitHub `owner/repo`, base branch, the fine-grained-token auth mode, and the selected Vault/Core Secrets logical name without receiving raw secret values. It returns redaction-safe `vault_requirements` so Vault can grant `github-token`. `website_git_connection_activate` can explicitly mark a prepared connection as grant-backed when a grant reference is provided with `confirm_no_raw_secret=true`; runtime Core Secrets delivery during import also marks the connection grant-backed after a successful private clone. Raw GitHub tokens are never accepted by the app frontend, CLI, MCP, logs, or summaries. For private GitHub imports, Website Studio uses the Vault-delivered `github-token` only inside the backend Git process through `GIT_ASKPASS`, so the token is not placed in the clone URL or command-line arguments. During approved publish, GitHub-backed sites use the same Vault-delivered token in backend memory only to push changed files to a Maverick branch and open or reuse a pull request; existing Website Studio PR branches are updated with `force=false`, and non-fast-forward conflicts block publish instead of force-pushing.

The app exposes path-safe file reads and writes. Writes and patches require `expected_hash`; new file writes use `expected_hash=new`; source tree mutations are serialized per site so stale writes are rejected instead of silently overwriting concurrent edits. Git-backed sites can run `website_sync_source` to refresh from the retained source reference. Sync uses the same safe clone path as import, strips Git metadata, validates the imported tree, records a `sync_run`, and blocks with `blocked_local_changes` when the current working tree has unpublished local changes unless the caller explicitly supplies `confirm=true` after review. Diff compares the current working tree against the active revision snapshot. Reference payloads include `app_page` and `/app/website-studio/...` deep links for implemented site, page, route, asset, revision, and publish-request entities. Imports, syncs, writes, index rebuilds, and builds persist a `source_profile` and `source_version` so hot preview loads do not need to rescan the source tree. `website_bootstrap` returns the minimal UI startup shape: sites, selected site, routes-only sitemap, and the latest compatible preview for the requested route; full status, diff, report, and asset inventory load after first paint.

Preview creates a persisted preview record, a runtime health session, and a `preview_url` that points at Website Studio's app-owned `preview-runtime` frontend with a runtime version query parameter so already-existing previews do not keep loading stale preview wrappers from browser cache. Compatible ready previews are reused by route plus runtime build id or current `source_version`, so normal frontend refresh/navigation does not create duplicate preview records and bootstrap will not reuse stale HTML after source edits or new runtime builds. `website_preview_document` caches prepared HTML by preview/build/source version/route/runtime version. Preview documents inline local stylesheets and local scripts on the backend using the same path-checked media resolver as `/media`, then replace resolved media URLs with app-approved `/api/apps/website-studio/backend/file/<token>` gateway URLs whenever possible. Each gateway URL is a random, short-lived, public capability scoped to one exact resolved file path through `allowed_paths`; valid capabilities are reused for the same file path and ETag until their remaining TTL is low, so route changes keep stable browser-cacheable asset URLs. Maverick core can serve images, fonts, scripts, and video directly with cache headers, ETag, range support, and cross-origin-safe headers without launching the Website Studio backend and without relying on cookies from the nested opaque iframe.

While the first route document is being prepared and mounted, the canvas stays covered by the Maverick workspace loader with a page-aware label such as `Caricamento Home` or `Caricamento Privacy Policy`. The nested document emits a minimal ready message directly at `DOMContentLoaded`, before DOM snapshots, computed-style inspection, asset coverage, or other observability work; images, fonts, media, and the full preview report continue in the background. Warm cached route activation emits the same document-ready contract immediately, avoiding both a white flash and an unnecessary wait for media or diagnostics.

The runtime frontend fetches `website_preview_document`, receives a bounded source map plus an `asset_gateway` capability map, replaces CSP placeholders with the current app origin, synchronously normalizes local images, videos, fonts, CSS URLs, srcsets, and inline-script media references to direct `/backend/file/<token>` URLs when mapped, and immediately mounts the selected website HTML as a UTF-8 Blob document in a nested opaque-origin sandbox iframe. The injected preview asset broker is now a direct-URL normalizer for later DOM/style mutations; it prefers the same capability map for dynamically inserted local assets, falls back to `/backend/media` only for unknown unmapped paths, and does not fetch asset bytes, use `postMessage` for asset transfer, or rewrite media to child-owned blob/data URLs. Video, audio, and source elements therefore stay streamable browser resources and can use HTTP `Range`. Preview CSP allows HTTPS image, media, font, and stylesheet assets so public web fonts/CDN media can render, while external scripts and XHR/fetch connections stay blocked. Preview reads and media loads do not emit `maverick.app.data-changed` events.

Sidebar page, route, section, anchor, and component selections keep the central preview runtime iframe mounted whenever the selected site/build/runtime context is still compatible. The app sends a bounded navigation message to the already-loaded preview runtime, and the runtime caches prepared preview documents, local asset gateway URLs, and a bounded set of already-mounted nested page frames for the life of that iframe. Returning to a previously visited page therefore switches back to the live page frame instead of recreating the Blob document, while shared images, fonts, scripts, stylesheets, and media keep their browser-loadable URLs across sidebar navigation. Source-change events still clear the preview caches and force a fresh runtime load.

`website_preview_report` turns a prepared preview into an app-owned observability report for agents and review workflows. It resolves local preview asset references from the prepared document plus the source map, reports image/font/video/script/style coverage, includes candidate DOM selector-to-source-file hints, normalizes those hints into component candidates, records acceptance checks, and can compare against a previous `baseline_report_id` for before/after chat edits. Its source-map defaults to visual/editable source candidates and an `asset_index` of assets referenced by the visible preview; callers must pass `include_inventory=true` to request broader source inventory and imported asset inventory for debugging. The preview runtime also injects a browser-side probe inside the nested sandboxed document; it posts bounded DOM snapshots, computed styles, `document.fonts` readiness, resource entries, asset readiness, direct asset-normalizer state, target selector readiness, and console logs to the parent as `maverick.website-studio.preview-report` without giving the parent same-origin DOM access.

`website_navigation_analyze` is the UI-facing visual navigation boundary. It keeps `website_sitemap` as the compatibility source inventory surface, but returns only site, canonical visual pages, non-duplicate visual routes, observed sections, anchors, filtered builder-grade component candidates, preview/build status, analysis coverage, and agent warnings. Repository metadata, server config, backend admin source, package manager files, build config, lockfiles, and unreferenced source inventory remain available to agents through inventory/search/read-file surfaces but are not navigable sidebar objects. `website_page_context` follows the same visual default: page, route, component, changed-file, and persisted preview-report source candidates are filtered, component context reports component-owned `source_files` at top level and page candidates separately as `page_source_files`, rendered media appears as `visual_assets`, and full routes/assets/report inventory is included only when callers pass `include_inventory=true`.

PHP and Node-build sites use bounded app-owned runtime adapters. `website_build_validate` prepares a runtime build record for `php` and `node_build` sources, copies an immutable runtime artifact, and indexes rendered routes when route rendering succeeds. Successful runtime renders are also crawled for same-origin internal links up to Website Studio's bounded route budget, so PHP/Node sites can surface rendered routes that were not present in the static sitemap. Node asset builds run only when `package-lock.json` is present and the npm `build` script expands to allowlisted local build commands such as Vite, Astro, Gatsby, Next, Dart Sass/PostCSS/CSSNano, Webpack, or a tightly-scoped generated-file `rm`. Build binaries must resolve from the imported site's own `node_modules/.bin`; Website Studio does not fall back to host-global Node binaries. Dependency installation uses `npm ci --ignore-scripts --no-audit --no-fund`; the app contract therefore declares outbound access to `registry.npmjs.org` in addition to GitHub. Node runtime artifacts detect common generated static docroots such as `dist`, `build`, `out`, and `public` before rendering routes. Build and PHP preview subprocesses run under a declared runtime process policy: constrained environment variables, app-local ephemeral `HOME`/`TMPDIR`, timeout enforcement, POSIX process-group cleanup, and best-effort POSIX CPU, memory, open-file, and process limits. Arbitrary shell commands, unsupported package managers, native-binary build tools such as `node-sass`, inline credentials, host paths in runtime logs, and unbounded scripts are blocked or redacted before surfacing. PHP preview uses the local `php` executable and an isolated loopback server on `127.0.0.1`; servers are keyed by runtime root/docroot/router, recorded in a temporary PID registry with process-group metadata when available, and kept alive for a short TTL so route reloads across backend subprocesses behave more like browser navigation without leaving long-lived processes behind. If `php` is not available in the host runtime, PHP sites are blocked with `php executable is not available to the Website Studio preview runtime` instead of falling back silently.

Publishing now uses explicit Website Studio approval events plus an authenticated actor policy. A publish request requires at least one working-tree diff and a passing deterministic build validation. `website_approval_record` creates one scoped approval for `publish` or `rollback` only for an authenticated Maverick user whose workspace role is owner/admin or whose platform role is admin/operator; `approved_by` must match that actor when supplied. Approvals are single-use and must match the selected site, action, and target id. `website_publish` consumes a publish approval, snapshots the working tree as a published revision, marks the publish request and changeset published, and records a deployment. `website_rollback` consumes a rollback approval, restores the selected revision into the working source tree, records a new rollback revision, and records a rollback deployment.

`website_publish_target_configure` can bind a site environment to a managed static publish target. Approved managed-static publish copies the selected working source into an immutable deployment artifact under `data/website-studio/sites/<site_id>/deployments/<artifact_id>/public`, records a redaction-safe `maverick-managed-static` source reference with explicit generic-hosting binding metadata, and marks the deployment mode as `maverick_managed_static`. Managed-static target config now carries `public_url`, `custom_domain`, `certificate_status`, `cache_policy`, `cdn_status`, and `verification_status`; deployment records expose `platform_binding.public_binding_ready` only when the generic surface reports `platform_binding_status=bound` and a stable public URL is present. Pending targets keep explicit `missing_requirements` for generic static hosting, stable public URL, domain/certificate binding, and external HTTP verification. Build validation also prepares a static preview artifact under `data/website-studio/sites/<site_id>/builds/<build_id>/public` whenever a static route is available. This implements Website Studio's Phase 3 app-side orchestration boundary plus Phase 3A runtime readiness: artifact selection, publish request, deployment records, rollback intent, app-owned static/PHP/Node preview runtime adapters, rendered route records, runtime health records, and public-binding readiness metadata. Generic platform hosting concerns such as actual custom-domain provisioning, certificate issuance, CDN/cache enforcement, public production binding, external deployment writeback, and long-running managed production process hosting are post-1-2-3-3A platform work until core exposes reusable hosting/runtime surfaces.

GitHub-backed sites with an activated grant receive a redaction-safe `github_pull_request` deployment source reference containing the target base branch, deterministic `maverick/<site_id>/<publish_request_slug>` working branch, commit sha, and pull-request URL unless the environment is explicitly configured for `managed_static`. If the deterministic working branch already exists, Website Studio updates it without force; GitHub non-fast-forward rejection blocks the publish and leaves PR creation untouched. If a GitHub source is configured for Git PR publishing but the grant or runtime secret delivery is missing, publish is blocked before consuming approval. The app still does not deploy to external hosting providers or run arbitrary production commands. CMS, commerce, external deployment writeback, custom domains, CDN, and certificate automation remain undeclared because they are not implemented.

`website_list_changes` exposes bounded change state for agents: working diff summaries, changesets, publish requests, approval events, build validation records, deployments, and revision metadata for a selected site. It accepts `limit`, `offset`, `include_logs`, and `diff_limit`, returns pagination metadata for each history section, and compacts long logs unless full logs are explicitly requested. `website_builds_list` follows the same pagination and compact-log behavior. These actions are read-only and do not push, deploy externally, or write back to third-party systems.

`website_maintenance_prune` applies app-owned retention to operational history. It supports dry-run and scoped execution, keeps the newest build records/artifacts, newest preview records per route, and newest runtime health sessions according to bounded policy defaults, and returns deleted counts plus deleted paths. The default policy keeps 10 builds, 3 previews per route, and 20 runtime sessions; operators should run dry-run during routine workspace maintenance and prune only after reviewing the reported counts. It never deletes source trees, revisions, deployment artifacts, publish requests, approvals, or site records.

## Frontend Layout

The central workspace frame is reserved for the selected website only. It does not show the editor, diff, preview, or publish controls; those operations are handled through agent-facing MCP/CLI/backend surfaces.

When no site exists, or when the user clicks `New` in the sidebar footer, the central frame shows a concise conversational guide instead of direct import controls. It asks the user to write in chat that they want to connect a website, then points them to the two supported onboarding paths: share a Drive/Storage ZIP link or connect a GitHub repository with the required secret stored in Vault.

The direct import work is handled by agents through the declared Website Studio, Storage, and Vault surfaces. For ZIP onboarding, an agent should obtain or localize the ZIP through Storage, call `website_import_zip`, and preserve the Storage artifact reference when available. For GitHub onboarding, an agent should prepare the repository connection with `website_git_connection_prepare`, tell the user to store a fine-grained GitHub token in Vault/Core Secrets as `github-token`, activate the grant with `website_git_connection_activate`, and then call `website_import_git`. Raw GitHub tokens are never accepted in chat, frontend fields, logs, or summaries.

The central preview keeps first paint focused on the selected website. The compact read-only info panel loads `website_site_status` and `website_list_changes` only when the panel is opened. It intentionally does not expose production action buttons.

### Versioned performance read model

`workspace_snapshot.v1` is the shared compact read model for the main frame and sidebar. It contains the minimal project list, active project, granular resource versions, indexed navigation, materialized working-file count, latest build summary, and latest compatible preview. Navigation and working state are persisted in `project_read_models` by `source_version`; build, preview, and activity summaries remain independently versioned SQL segments. Clients can send `known_versions` and receive `not_modified` without a repeated snapshot body.

The initial UI read excludes asset inventory, diff patches, complete history, build logs, preview reports, and deployment history. Those stay on explicit detail actions. Both iframe clients keep a memory/session snapshot, deduplicate concurrent reads, render stale data while revalidating, and invalidate only affected resource segments. Source/navigation changes reset preview state; activity, settings, and view-selection changes do not. Preview route caching is explicitly bounded. SQLite schema initialization is process-cached after its migration check rather than replaying the complete idempotent DDL on every read.

The base-shell sidebar widget owns visual site navigation. It shows search first, then the site selector, then the selected site's imported site root, canonical pages, meaningful sections, anchors, filtered component candidates, and warnings from `website_navigation_analyze`. Empty route/status/warning groups are not rendered as tree content; runtime/build state is summarized on the site root badge and tooltip. It does not build navigation from the source inventory and does not expose backend/config files, lockfiles, README files, or unreferenced assets in the main tree. Page and route clicks open the matching preview route through the shell open-app contract; section, anchor, and component clicks also pass `target_selector` and/or `target_anchor` so the workspace preview can scroll/highlight the selected rendered element. Files touched by the working diff are summarized as modified status on visual nodes rather than as a file tree. The sidebar footer exposes `New` and `Info` actions only.

The visual test suite verifies the central preview on desktop and mobile and now covers the mounted-shell message contract by sending `maverick.app.navigate` for a route selection and `maverick.app.data-changed` for a refresh. The tests assert route-aware preview runtime URLs, refreshed changed-file state, nonblank screenshots, non-overlapping preview/info panel layout, and a runtime-wrapper regression where the document mounts before slow lazy media finishes loading while local assets remain direct browser-loadable URLs.

## Security Notes

- Website paths are normalized and constrained to the selected site source tree.
- ZIP import rejects absolute paths, `..`, ignored system files, excessive file counts, and excessive expanded size.
- Git import rejects inline credentials, allows GitHub HTTPS URLs or local repository paths inside the Website Studio data root, and runs Git with credential prompts/helpers disabled unless a prepared and activated GitHub connection receives its token through Core Secrets for private repository clone.
- GitHub connection preparation and activation store only repository metadata, selected auth mode, secret logical names, and redaction-safe grant references; raw GitHub tokens must stay in Vault/Core Secrets and are never accepted by the frontend.
- Build/preview supports deterministic static validation, immutable preview artifacts, allowlisted npm lockfile asset builds, bounded PHP route rendering when the host provides `php`, and an app-owned isolated preview runtime with timeout, process-group cleanup, constrained environment, and best-effort POSIX resource limits. Unsupported package managers, arbitrary dependency scripts, arbitrary shell commands, missing PHP binaries, and missing lockfiles fail closed with explicit runtime requirements.
- Runtime subprocesses receive app-local ephemeral `HOME` and `TMPDIR` directories outside the served docroot. OS-level sandboxing and network namespaces remain generic platform hardening gaps, so Website Studio's Phase 3A runtime must still be treated as a workspace preview boundary rather than production hosting.
- Publish and rollback approvals are explicit, scoped, single-use app records guarded by authenticated owner/admin or platform admin/operator policy. Public production binding remains blocked until generic platform hosting surfaces exist.
- The contract declares a required `file.content.write` Storage provider for user-uploaded ZIP artifact persistence; Storage, Vault, Memory, Chat, and App Store composition must happen through official app/core surfaces.

## Contract Notes

Website Studio is a source-available, forkable platform app. Its contract declares sandbox compatibility, app-owned SQLite/site storage, frontend/backend/CLI/MCP surfaces, sidebar widgets, website reference entities, standard Website Studio view-state actions, install/migrate/health hooks, outbound GitHub/npm requirements, and a required Storage provider for imported ZIP persistence. App-level lifecycle export/import remains intentionally in standby: `supports_export` and `supports_import` are false until a concrete workspace export/import design is implemented and tested for Website Studio data.
